# secoem-VSS

Implements and compares two decision-stage formulations of the `secoem`
energy-community market-participation model, solved over stochastic
scenario trees:

- **HG** (`same_ren`) — the *hourly-grouped* chain,
  30 decision stages / 31 tree stages.
- **QHS** (`dif_ren`) — the *quarter-hourly-staged*
  chain, 102 decision stages / 103 tree stages.

Both are the same Pyomo optimization model (day-ahead + reserve + three
intraday markets + battery/wind/PV energy community), differing only in how
finely the decision stages are resolved. Everything in this repo exists to
generate the scenario trees, run both formulations against them, and produce
the three-way comparison in `Results/`: the scenario trees themselves, the
simulation results (computational cost and operating strategy), and the
Value of the Stochastic Solution (VSS) and its dynamic counterpart (VSSD).

## Repository layout

| Folder | Contents |
|---|---|
| [`HG/`](HG/) | The hourly-grouped model: code, data, scenarios, per-run results, VSS/VSSD batch machinery. |
| [`QHS/`](QHS/) | The quarter-hourly-staged model. Structurally identical to `HG/` (same codebase, forked per formulation). |
| [`scentree-gen-remote/`](scentree-gen-remote/) | Vendored copy of the `scentree` scenario-tree generator. Produces the `scenarios_AMPL_{HG,QHS}` trees that `HG/` and `QHS/` consume as input. |
| [`Results/`](Results/) | The notebooks and pre-computed CSV/JSON/figure exports that turn `HG/`, `QHS/` and `scentree-gen-remote/` output into the actual thesis chapter (`results.tex`) figures and tables. |

`HG/` and `QHS/` have no `README.md` of their own — everything about both
(they're structurally identical) is documented here.

## `HG/` and `QHS/` — the two formulations

The energy community consists of flexible demand (implicit modeling), a
wind farm, a solar farm and a battery energy storage system (BESS),
formulated as a multi-stage stochastic optimization scheduling energy
production, consumption and trading across the day-ahead, reserve and three
intraday markets. The model is implemented in Pyomo (replacing an earlier
AMPL formulation). `HG/` and `QHS/` are two instances of the same codebase,
forked to resolve decision stages at different granularity — everything
below applies identically to both, substituting `HG`/`same_ren` for
`QHS`/`dif_ren` as needed.

### Environment setup

Requires Python 3.11+ and the dependencies in `python_environment/optirec_env.yml`:

```sh
cd HG   # or QHS
conda env create -f python_environment/optirec_env.yml
conda activate optirec_env
```

| Path | Purpose |

| `pre_process_AMPL_to_Pyomo_scenario_data/` | `ampl_to_pyomo_scenario_files.py` — converts the AMPL `.dat` scenario files in `scenarios/` into Pyomo-compatible format, in place. |
| `codes/` | The Pyomo model and simulation pipeline (below), plus the VSS/VSSD layer. |
| `results/` | Per-run output, one subdirectory per scenario family (`results/<famscen>/DA/{ec,market}/<sim>/...`). **Gitignored** — regenerated by running the code, never pushed. |
| `results_batch_{same,dif}_ren.csv` | One row per batch-run scenario count, from `codes/batch_run_scenarios.py`. Feeds `Results/Execution of model/section_4_2_results_of_simulations.ipynb`. |

### Scenario file setup

Within `scenarios/`, each simulation has its own directory (e.g.
`FTC_100_2024/`), following the naming convention above. Within that
directory, each market's scenarios live under the name defined in the
market chain — for a full simulation, that means `DA/`, `RM/`, `IM1/`,
`IM2/` and `IM3/` subdirectories.

1. Copy the AMPL-formatted `.dat` scenario files into `scenarios/`, keeping that naming convention.
2. Convert them to Pyomo format:
   ```sh
   cd pre_process_AMPL_to_Pyomo_scenario_data
   python ampl_to_pyomo_scenario_files.py
   ```
   This reads the `.dat` files from `scenarios/`, converts them, and overwrites them in place.

### Running the base simulation

`config_definition.py` holds the static parameters of a simulation run —
`famscen_all` (the scenario family directory, e.g. `FTC_100_2024`), `SIMS`
(which days to loop over), result paths and the Gurobi `SOLVER_OPTIONS`
(`MIPGap`, `TimeLimit`, `Threads`, …).

```sh
cd codes
python modular_ec_run.py
```

This loads the scenario data from `scenarios/`, optimizes the energy
scheduling for every day in `SIMS`, and stores results (scheduled
production, consumption and trading strategies) under `results/`, in a
subdirectory named after `famscen_all`, further split by market.

```text
┌─ config_definition.py ───────────────────────────┐
│  SIMS = ["001", …]             # days to loop over│
│  famscen_all / paths / solver options …           │
└──────────────────────────────────────────────────┘
        │
        ▼
┌  modular_ec_run.py  (main loop) ┐
│  for sim in SIMS:               │
│    1. SimulationContext         │  ← paths, filenames, KPI holders
│    2. PreProcessor              │  ← loads + cleans data → DataPortal
│    3. InstanceManager           │  ← DataPortal → abstract model, derives prices / bounds / clusters
│    4. Solver (Gurobi)           │  ← solves the model, returns results
│    5. PostProcess               │  ← NAC checks, stores results into files and logs
│    6. InstanceManager.next_IC() │  ← updates BESS SoC for the next day
│    ⤷ append ctx to list         │
└─────────────────────────────────┘
        │
        ▼
SimulationSummaryWriter  ➜  tables + ec_<family>_summary.out
```

| File | Main class | Responsibility |
|---|---|---|
| `codes/simulation_context.py` | `SimulationContext` | Data container: paths, filenames, solver time, objective-function results for one simulation. |
| `codes/preprocessing.py` | `PreProcessor` | Loads the corresponding scenario data, using `PreviousMarketResultsLoader` to pull in cleared results of previous markets. |
| `codes/instancemanager.py` | `InstanceManager` | Builds and populates the Pyomo instance (`compute_instance()`), and carries initial conditions (e.g. BESS SoC) to the next run (`next_initial_conditions()`). |
| `codes/solver.py` | `Solver` | Wraps Gurobi: loads `SOLVER_OPTIONS`, times the solve, stores the raw `SolverResults`. |
| `codes/postprocess.py` | `PostProcess` | Runs NAC checks and `store_results()`, writing simulation output to files and logs. |
| `codes/simulation_summary_writer.py` | `SimulationSummaryWriter` | Writes the final summary across all simulations once the loop completes. |
| `codes/ec_model.py` | Pyomo `AbstractModel` | The mathematical formulation of the model. |
| `codes/modular_ec_run.py` | `__main__` | The main loop described above. |
| `codes/config_definition.py` | — | Static, per-run-invariant configuration: solver options, file paths, `famscen_all`, `SIMS`. |

### VSS/VSSD layer

It implements the static and dynamic VSS chains of Escudero, Garín, Merino &
Pérez (2007), *"The value of the stochastic solution in multistage
problems"*, 48–64, against the EC model's six market-clearing
macro-stages (`DA, RM, IM1, IM2, IM3, IB`):

| File | Role |
|---|---|
| `codes/vssd/edev_vssd.py` | Pure math: `compute_edev_t`, `compute_vssd`, `compute_vssd_t` (Definitions 4–6). Infeasible `EV_g` groups at a stage are excluded and remaining weights renormalized rather than propagating `-inf` (see the module docstring for the exact policy). |
| `codes/vssd/run_vssd.py` | Orchestrates the **dynamic** chain: solves RP, the per-group `EV_g` subproblems, and `EDEV_t`/`VSSD_t`/`VSSD`, then validates Propositions 4–7. Entry point: `compute_vssd_chain(sim)`. |
| `codes/vssd/run_static_vss.py` | Orchestrates the **static** chain: a single classical EV solve (all random parameters at their unconditional expectation) fixes each stage, giving `EEV_t`/`VSS_t` (Definition 1). Entry point: `compute_static_chain(sim)`. |
| `codes/batch_run_vss.py` | Batch driver: runs both chains for sim `"001"` of every scenario-count folder under a `scenarios_AMPL_*` directory, appending one summary row per run to a CSV. Mirrors `batch_run_scenarios.py`'s process-per-folder / core-pinning / resumable-CSV design. |
| `codes/batch_run_scenarios.py` | The non-VSS counterpart: just runs the base DA pipeline (no VSS/VSSD) per scenario-count folder, for `results_batch_*.csv`. |

Both `run_vssd.py` and `run_static_vss.py` are fully decoupled from the main
pipeline — they import `config_definition`/`simulation_context`/`preprocessing`/
`instancemanager`/`solver` exactly as `modular_ec_run.py` does, but are never
called from it and never modify it.

**Per-run VSS output** (under `results/<famscen>/DA/ec/001/`, alongside the
normal simulation output):

| File | Written by | Contents |
|---|---|---|
| `static_vss_results.csv` | `run_static_vss.py` | `EEV_t`, `VSS_t`, excluded weight for `t=1..6`; trailer rows `RP`, `EV`. |
| `edev_vssd_results.csv` | `run_vssd.py` | `EDEV_t`, `VSSD_t`, excluded weight for `t=1..6`; trailers `RP`, `VSSD`. |

#### Running it

Single scenario family, both chains, one day (`sim="001"` by default via
`config_definition.SIMS`):

```sh
cd HG/codes   # or QHS/codes
python vssd/run_static_vss.py      # writes static_vss_results.csv
python vssd/run_vssd.py            # writes edev_vssd_results.csv
```

Batch, across every scenario-count folder of a generated tree family:

```sh
cd HG/codes
python batch_run_vss.py \
    --root /path/to/scenarios_AMPL/scenarios_AMPL_same_ren \
    --ren-type same_ren \
    --branch-label 15min_ren_same \
    --csv ../results_vss_same_ren.csv \
    --lanes 16 --threads 4 --time-limit 14400
```

Useful flags: `--only 50,60,70` to restrict to specific scenario counts,
`--project-root` to redirect where `results/<famscen>/...` lands (e.g. a
scratch directory for a trial run, instead of overwriting the real
`results/`), and `--core-offset` to run HG's and QHS's batches concurrently
on the same machine without their pinned-core ranges colliding. The CSV is
resumable: rows already marked `status=ok` for a given
`(ren_type, num_scenarios_folder)` are skipped on rerun.

- Re-running a simulation overwrites its previous results.
- `results/` is gitignored in both `HG/` and `QHS/` to keep the repository clean.

## `scentree-gen-remote/`

A vendored copy of the [`scentree`](https://github.com/mmobec/scentree)
package: generates scenario trees for multistage stochastic programs from
historical/forecast time series (electricity prices, wind and PV
generation), via statistical models plus scenario-reduction algorithms. Its
`build_scenarios_AMPL.py` / `scenarios_json_to_AMPL.py` scripts produce the
`scenarios_AMPL_{same_ren,dif_ren}/FTC_..._sc<N>_.../` trees that `HG/scenarios/`
and `QHS/scenarios/` are populated from (after the AMPL→Pyomo conversion
described above).

See `scentree-gen-remote/README.md` and `scentree-gen-remote/docs/` for
generator usage; this repo only depends on its output format, not on
editing it. Its own generated trees (`same_ren_scentree/`, `dif_ren_scentree/`,
`scenarios_AMPL/`) are gitignored — kept locally for re-running simulations,
never pushed.

## `Results/` — notebooks and figures for `results.tex`

Three subfolders, one per thesis-chapter section, each regenerating that
section's figures/tables from data files that sit alongside the notebook
(the notebooks document their own exact data sources and reproducibility
caveats in their first cell — read that before trusting a number out of
context):

| Folder | Section | Main notebook | Data it reads |
|---|---|---|---|
| [`Scenario tree results/`](Results/Scenario%20tree%20results/) | Results from scenario generation | `section_4_1_scenario_generation.ipynb` | `scenario_tree_summary.csv`, `scenario_tree_stage_stats.csv`, `HG_sc100_results_1.json`, `QHG_sc100_results_1.json` |
| [`Execution of model/`](Results/Execution%20of%20model/) | Results of simulations | `section_4_2_results_of_simulations.ipynb` | `results_batch_dif_ren.csv`, `results_batch_same_ren.csv` (copies of `QHS/`'s and `HG/`'s own), plus `../Scenario tree results/scenario_tree_summary.csv` |
| [`VSS computation/`](Results/VSS%20computation/) | Results of the value of the stochastic solution | `section_4_3_value_of_stochastic_solution.ipynb` | every run's `static_vss_results.csv` / `edev_vssd_results.csv` under `../../HG/results/` and `../../QHS/results/` (globbed, so adding runs needs no notebook edit) |

Each folder also carries earlier, broader exploratory notebooks that the
`section_4_*` notebooks superseded for the actual thesis figures but that
still hold useful deep-dive analysis:

- `Scenario tree results/analisis_scenario_generation.ipynb` — structural
  study of the raw trees themselves (topology, probabilities), independent
  of downstream solve performance.
- `Execution of model/analises_results.ipynb` — single-run deep dives,
  including a matched-model-size (`num_scenarios_reduced`) comparison between
  HG and QHS.
- `VSS computation/section_4_3_vss_matched_146.ipynb` — a two-run companion
  to the main VSS notebook: instead of sweeping every available run, it
  computes and compares the static/dynamic chains for exactly one matched
  HG/QHS pair (same retained scenario count, `\|Ω\| = 130`), which is the
  controlled apples-to-apples comparison the full sweep can't offer on its
  own. `vss_comparison_qhs_hg.md` and `vss_comparison_chart.png` in the same
  folder are a hand-written report/chart version of that same matched
  comparison.

`Execution of model/results/` is the raw per-run `.txt` solution export
(~280 MB, thousands of files) that the analysis notebooks can optionally
dig into — **gitignored**, kept local only; the CSVs above are what the
notebooks actually run against by default.

## End-to-end workflow

1. **Generate scenario trees** — `scentree-gen-remote` → `scenarios_AMPL_{same_ren,dif_ren}/`.
2. **Convert to Pyomo format** and place under `HG/scenarios/` / `QHS/scenarios/`
   (see *Scenario file setup* above).
3. **Run the base simulation batch** — `codes/batch_run_scenarios.py` →
   `results_batch_{same,dif}_ren.csv` (feeds `section_4_2`).
4. **Run the VSS/VSSD batch** — `codes/batch_run_vss.py` → `results_vss_*.csv`
   and, per run, `static_vss_results.csv` / `edev_vssd_results.csv` under
   `results/<famscen>/DA/ec/001/` (feeds `section_4_3`).
5. **Regenerate figures** — run the `section_4_1`/`section_4_2`/`section_4_3`
   notebooks under `Results/` against the outputs of steps 1–4.
